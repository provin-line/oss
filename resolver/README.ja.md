# resolver — DID Document 解決
> 日本語版 — English: [README.md](README.md)

`Resolver` インターフェース（`Resolve(ctx, did string) (*did.DIDDocument, error)`）とその実装群。`Resolve` は nil でない文書か nil でない error のどちらかを返し、どちらも nil にはしない。

## 実装

| パス | 状態 | 動作 |
| --- | --- | --- |
| `local/` | 実装済み | インメモリストア。テストおよびフィクスチャ用 |
| `cache/` | 実装済み | TTL・バイト有界のキャッシュデコレータ（`Resolver`） |
| `grpc/` | 計画中 | レジストリの DIDService への ConnectRPC 呼び出し |
| `multi/` | 計画中 | ホームレジストリ優先、追加レジストリへのフォールバック |

`local/` と `cache/` は現時点でこのモジュールに存在する。`grpc/` と `multi/` の行と、以下の規約における両者の記述は、意図された契約を述べたものである。

## 規約

- `cache/` は成功した解決のみをキャッシュし、エントリは充填から固定 TTL で失効する（ヒットで延長しない）。ヒット毎に新規パースしたドキュメントを返し（`*did.DIDDocument` の共有なし）、成功した解決をエラーに変換することは決してない — キャッシュ不能なドキュメントはキャッシュせずにそのまま返す。エントリ数とバイト数の両方の上限が必須（解決キーは未認証入力から到来するため）。鮮度と脅威の議論はパッケージコメント参照。
- `grpc/` は返されたドキュメントの ID がリクエストした DID と一致することを検証する（レジストリ置換攻撃への防御）。
- `multi/` のフォールバックは**接続エラー時のみ**発動する。いずれかのレジストリからのアプリケーションエラー（not-found・パーミッション）は信頼できる応答であり短絡する — フォールバックは否定パスの設定エラーを隠蔽してはならない。
- ホーム URL は DID の `registry` セグメントから導出される（`https://{registry}`）。デフォルトレジストリのエスケープハッチまたは明示的なセグメント→URL マップ（compose・マルチレジストリ開発環境）でオーバーライド可能。
